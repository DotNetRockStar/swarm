SWARM System Guide

SWARM is a free, secure, strictly peer-to-peer media streaming suite — Plex-like, but your media never leaves machines you own. You stream your own music and video from your own computer to your own devices, end-to-end encrypted.

No cloud for your media

Video and audio flow directly device → device. There is no relay server in the middle and no copy stored anywhere else.

A coordinator that can't watch

A small hosted server helps your devices find each other. It only sees connection setup — never the media, which it also could not decrypt.

Works great on your own Wi-Fi

On the same network, devices discover each other automatically and don't need the internet at all.

The short version

  1. You install the media server app on the computer that holds your movies, shows, and music, and point it at your media folder.
  2. You install the TV app on your Fire TV.
  3. The TV shows a short code; you approve it once in the media server app.
  4. The TV browses your whole library and plays it. If the TV and computer are on the same Wi-Fi it's a direct local connection; if they're apart, SWARM connects them over the internet automatically — still directly, still encrypted.

Glossary

TermMeaning
SwarmA private group of your devices that are allowed to see each other and share catalogs.

Devices & roles

SWARM has four kinds of participant. Only two of them ever touch your media.

Media server shipping

Desktop app on your computer. Holds the media, builds the catalog, decides direct-play vs transcode, and serves the bytes. The only device that reads your files.

Fire TV client shipping

The living-room app. Browses the merged catalog and plays. Stores only a small encrypted token and its own key — never your media.

Roku client planned

Groundwork exists (a plain-HTTP playback surface) because Roku's BrightScript can't speak QUIC. Not yet a shipping app.

STUN / rendezvous shipping

Hosted coordinator. Sees which devices are online and relays connection-setup messages. Never sees or could decrypt media.

Your browser shipping

Optional account web UI on the STUN server for creating a swarm and join codes. Media servers now provision their own swarms, so this is mostly a fallback.

Media server

The desktop app (macOS, Linux, Windows) that turns a folder of media into a private stream.

What you do

  1. Install and open the app. A window appears.
  2. Choose your media folder. On macOS you can also connect straight to a NAS over SMB.
  3. The app builds a catalog (posters, seasons, track art) in the background.
  4. Closing the window hides it to the system tray — streaming keeps working, and the app asks the OS to keep the computer awake until you pick Quit SWARM.

Optional extras

  • Local subtitles — generate English subtitles on your own machine with a downloaded speech model. Your media never leaves the computer.
  • Bandwidth limits — cap how much of your upload SWARM may use so streaming doesn't swamp the rest of your connection.

Architecture ENGINEER

  • Tauri app: a Rust core plus a vanilla-JS web dashboard (apps/server/ui, no framework). The GUI process owns ServerCore — there is no separate headless server binary. Hiding the window does not stop streaming.
  • Binds 0.0.0.0 (not just loopback) so a real LAN device can reach it.
  • Persists media, scraper, streaming, and AI settings in <app data dir>/settings.json; peer trust and pairing state in server-state.sqlite.
  • Requires FFmpeg + ffprobe at runtime for probing and HLS transcode. Building the app needs CMake because whisper.cpp is linked into the native binary.

Durable background work

Long-running jobs (local Whisper subtitles, and the pattern for future analysis/waveform work) run as a relational-SQLite job queue with checkpoints: completed sections survive an app restart, the worker pauses automatically while a client is streaming, and a live progress panel sits at the top of the dashboard's Media tab. Completed WebVTT tracks then appear in the TV player's normal subtitle controls.

Direct play only needs the source file's own bitrate to fit.

TV clients

Fire TV shipping

  1. Install the SWARM app on your Fire TV.
  2. On first run choose Connect through SWARM (across the internet) or pick a media server the app already found on your Wi-Fi.
  3. The TV shows a short code. Enter and approve it once in the media server app.
  4. The TV opens your library. Pick something and play. If it stutters on your connection the picture quality steps down automatically and recovers when the network frees up.
  • Native Kotlin, single-activity Jetpack Compose for TV (androidx.tv:tv-material), minSdk 25 (Fire OS 6+, 2018+ devices). Gradle multi-module: :core (pure Kotlin/JVM) and :app (Android).
  • :core hand-mirrors swarm-core wire types with kotlinx.serialization (JsonNamingStrategy.SnakeCase reproduces serde's rename_all). Every test fixture was captured from real serde_json::to_string output, so :core tests are a genuine cross-language compatibility proof.
  • PeerQuicClient (kwik) mirrors swarm_p2p::endpoint: mTLS with a client cert, post-handshake fingerprint pinning, one-request-per-QUIC-stream framing.
  • PeerLoopbackProxy bridges standard HTTP (what Media3/ExoPlayer speaks) to the peer protocol via http://127.0.0.1:<port>/<serverId>/<peerPath> URLs, translating Range / If-None-Match and streaming the body back.
  • Secrets: AndroidTokenStore wraps Keystore-backed EncryptedSharedPreferences (AES-256-GCM) for the access token; AndroidDeviceIdentity generates a real non-exportable AndroidKeyStore EC keypair with a self-signed cert and exposes its SHA-256 fingerprint.
  • The release manifest disables cleartext HTTP/WS (Appstore compliance); the debug build allows it for local testing against non-TLS dev endpoints.

Roku planned

Roku's BrightScript has no QUIC implementation and no realistic path to build one. The media server therefore also exposes an always-on plain-HTTP(S) pairing + playback surface (apps/server/src/http_media.rs) as groundwork for a future Roku client. It is a second, independent HTTP surface on ServerCore — not a replacement for the QUIC transport every current peer uses.

Engineer — why it's still safe without a device credential /pair/begin and /pair/poll are unauthenticated by definition (an unpaired device has no credential). That is compensated for, not ignored:
  • require_lan rejects anything not on a private / link-local / loopback address.
  • reject_cross_site rejects any request carrying Sec-Fetch-Site or Sec-Fetch-Mode headers at all — real device HTTP clients never send these; only a browser's fetch()/XHR does. This blocks a malicious LAN webpage whose own IP would pass the LAN check.
  • A per-IP fixed-window rate limiter caps /pair/begin.

STUN / rendezvous server

The one hosted piece. It is infrastructure, not something an ordinary user configures.

What it does — and doesn't

It doesIt never does
  • Tell your devices which of your other devices are online.
  • Pass small "let's connect" messages between them.
  • Hand out the short code your TV shows so you can approve it.
  • See, store, or relay any media.
  • Hold anything it could use to decrypt your streams.
  • Store your codes, tokens, or claims in readable form — it keeps only hashes.

Deployment shape ENGINEER

  • Docker Compose: the Rust service + Caddy. Caddy terminates HTTPS/WSS on TCP 443 (automatic ACME certs); the service receives reflector traffic directly on UDP 443 and UDP 3478. SQLite + Caddy state in named volumes.
  • Hosts both signaling/reflection and the short-lived TV activation exchange. Media servers provision their own private swarms with a stable local owner claim; TVs display a temporary code only the owning media server can approve.
  • Stores hashes of owner claims, device tokens, activation poll tokens, and codes — never their plaintext.

Reflector (reflexive address discovery)

UDP datagram b"bind" → JSON reply {"ip": "<observed ip>", "port": <observed port>} (≤512 bytes). Listens on UDP/443 (primary) and UDP/3478 (fallback); live ports are advertised in hello_ack. Byte-compatible with the retired Batocera.Drone Edge reflector.

Signaling session

  1. Device opens WSS, sends hello {protocol_version, access_token, device_id, capabilities?}.
  2. Server validates and replies hello_ack {session_id, observed_addr, reflector_ports}.
  3. Server pushes presence deltas for devices sharing ≥1 swarm. Media servers fold streaming {transcode_capacity, active_sessions, hw_accel} into their presence.
  4. ping/pong keepalive (~30s, client-driven). Reconnect with capped exponential backoff.
  5. signal {to, payload} is relayed only between devices sharing a swarm; the server stamps from and never interprets payload beyond routing.

LAN connections

When your TV and media server are on the same network, SWARM prefers a direct local connection and the internet service is optional.

  1. The media server announces itself on your Wi-Fi. The TV lists it automatically — no address to type.
  2. The first time, the media server owner opens a pairing window and the TV enters a six-digit code. That establishes trust between exactly those two devices.
  3. Every later connection reuses that saved trust and goes straight to a direct local stream.

If the TV can't find the server A VPN on the computer is the usual cause — it can hide the computer's real local address. Also make sure both devices are on the same Wi-Fi (not a "guest" network).

STUN-free LAN discovery and pairing ENGINEER

  • Media servers advertise _swarm-peer._udp.local. over mDNS with their QUIC port, certificate fingerprint, and local pairing port. Android clients browse it with DNS-SD and construct the same pinned SwarmDevice shape a STUN roster would produce — so catalog and playback traffic continue over the existing mutually authenticated QUIC transport and never pass through the pairing socket.
  • Discovery is not authorization. For a first connection the server owner explicitly opens a five-minute, single-use pairing window and enters its six-digit code on the client. The client submits its name and certificate fingerprint from a private/link-local source address. The server persists that fingerprint in server-state.sqlite and adds it to AllowedPeers. Revoking the local peer removes it from both persistent storage and the live allow-list.
  • Both server processes bind 0.0.0.0 for LAN reachability. run_now.sh prints a LAN URL and works around an active VPN skewing the detected local IP.

Connecting across the internet

When devices are on different networks, SWARM still connects them directly — it just needs the STUN server to introduce them first.

  1. Both devices tell the STUN server they're online.
  2. Each device asks the STUN server "how does my address look from outside?"
  3. Through the STUN server they swap those addresses and then both start sending packets to each other at the same moment, so each home router lets the other side in.
  4. Once the path is open they run an encrypted connection over it and stream. The STUN server is no longer involved.
  5. If your router is too restrictive to punch through, SWARM shows a diagnostics screen with guidance (enable UPnP, forward a port, or use the same network). There is deliberately no fallback relay.

Connection establishment (initiator I → responder R) ENGINEER

  1. Both sides gather candidates: lan (local interface addrs), reflexive (from the reflector, socket kept open), forwarded (UPnP/NAT-PMP-mapped or manually forwarded port — server role only).
  2. I sends signal{Offer {punch_id, candidates, cert_fingerprint}}; R replies signal{Answer {...}}.
  3. If R has a forwarded candidate, I connects directly — no punching.
  4. Otherwise simultaneous hole punch: both sides send PUNCH_MAGIC (b"swarm-punch-v1") to every remote candidate, LAN first, 20 attempts × 200 ms, while listening on the reflector socket. First received magic → reply and report signal{Punched {punch_id, ok: true}}. Both sides proceed only after mutual confirmation.
  5. QUIC handshake (TLS 1.3) over the punched 4-tuple. Both sides present their self-signed device certs; each verifies the peer's cert SHA-256 equals the pinned fingerprint. Any mismatch is fatal.
  6. On total failure: surface the diagnostics UX (NAT type, UDP reachability, guidance). There is no relay by design.

Route memory: persist the last successful candidate per peer and try it first next time — preference changes, the trusted candidate set never widens.

Catalog & playback

  • One merged library. If you run more than one media server, the TV shows a single combined catalog. The same movie on two servers is one entry with two sources.
  • Best source automatically. At play time the TV picks the fastest available source and falls through to another if one drops mid-stream.
  • Direct when possible. If your device can already play the file, it plays untouched. Otherwise the media server converts it on the fly to a quality that fits your connection, stepping down and back up as needed.
  • Subtitles from sidecar files next to your media, and optionally generated locally on the media server.

Catalog identity ENGINEER

  • entry_key = sha256(lowercase(relative_path with / separators))[:24] — per-server key.
  • fingerprint = sample-fp-v1 (MD5 over size:u64-LE + whole file if ≤192 KiB, else head/middle/tail 64 KiB windows) — cross-server identity. Clients merge manifests on fingerprint; multiple servers holding the same fingerprint become alternate sources for one entry.

Source selection (client, at play time)

Best-first with fall-through on network error, abort on definitive error: online (hard gate) → direct-play-compatible → LAN-tier route → last-successful-route recency → measured signaling RTT → minus transcode saturation. Mid-stream failure re-resolves to the next source at the current position.

Playback negotiation

PeerRequest.playback (only on /play/*) carries the client's CapabilityProfile, integer resume position, and direct-play preference over the pinned QUIC transport — the rendezvous service is never trusted with the playback decision. A successful PlaybackPlan returns mode, a session-scoped peer path, and a hard max_bitrate.

Security

SWARM's core promise: your media flows only between devices you own, encrypted end to end, and the one hosted server is structurally unable to see it.

What protects your media

ConcernHow SWARM handles it
Someone intercepting a streamEvery media connection is encrypted (TLS 1.3 over QUIC). Devices only accept a connection from the exact certificate they recorded when first paired.
The hosted server being compromisedIt never carries media and holds nothing that could decrypt it. It stores only hashes of codes and tokens, so a database leak doesn't expose usable secrets.
A stranger's device joining your swarmDevices join only by redeeming a short-lived, single-use code that you generate, and — for a TV — you still approve the specific device by name afterward.
A malicious page on your Wi-FiThe local pairing endpoint rejects browser-originated requests and anything off your local network, and rate-limits attempts.
Your access token being stolen off a deviceIt's stored in the OS keychain / Android Keystore (encrypted at rest). You can revoke any device instantly from the media server.
Your NAS passwordOn macOS it stays in the system Keychain prompt and is never passed to or stored by SWARM.

Trust boundaries ENGINEER

Identity & trust

CredentialWhat it isStorage
User session Cookie session against the STUN web UI/API. Argon2id, opaque DB-backed, sliding expiry. Server-side row; revoke = delete.
Device access_token Opaque 256-bit bearer issued when an 8-digit, single-use, ~15-minute, swarm-scoped join code is redeemed at POST /api/v1/devices/register. Hashed server-side (revocation = delete row); encrypted on-device (OS keychain / Android Keystore).
Device certificate Self-signed, generated on first run, private key never leaves the device. SHA-256 fingerprint submitted at registration (the TOFU moment) and re-confirmed inside signal offers/answers. OS keystore. No CA, no hostname verification.

Peer authorization = shares ≥1 swarm AND the presented cert's fingerprint matches the pinned roster entry, enforced at QUIC accept.

Transport

  • All media: QUIC with TLS 1.3. Both sides present self-signed device certs; each verifies the peer cert's SHA-256 equals the pinned fingerprint. Mismatch is fatal. (kwik has no CA-less pinning callback, so the TV verifies getServerCertificateChain() itself and closes on mismatch.)
  • Control/signaling: HTTPS/WSS terminated by Caddy with automatic ACME certificates.
  • PROTOCOL_VERSION travels in hello; the server rejects mismatches with error {code: "protocol_version"} so old apps get a clear update prompt.
  • REST evolution: requests strict (deny_unknown_fields), responses extensible.
  • Release Android manifest disables cleartext HTTP/WS entirely (Appstore compliance); only the debug build permits it, for local non-TLS dev endpoints.

Input & resource safety

  • entry_key values must pass entry_key::is_valid_entry_key before any filesystem lookup.
  • Session ids are random 128-bit values.
  • Status vocabulary: 400 for missing playback preferences, 429 for exhausted session/upload capacity, 503 for an unavailable/failed transcoder.
  • Streaming bandwidth is a server-wide reservation pool; response bodies are paced to the reservation rather than bursting onto the uplink — an availability and fairness control as much as a performance one.

What the STUN server can and cannot see

Can seeCannot see
  • Which devices are online and which swarms they share (presence).
  • Devices' observed public IP:port (reflexive discovery).
  • That a signal message went from A to B — it stamps from and routes.
  • Any media byte — media never traverses it, and there is no relay.
  • signal payload contents beyond routing (it never interprets them).
  • Playback decisions / capabilities — those travel peer-to-peer over pinned QUIC.
  • Plaintext codes, tokens, owner claims — only hashes are stored.

End-to-end flow: cold start to first frame

  1. Media server starts, scans roots, provisions its swarm, opens a WSS signaling session, advertises mDNS on the LAN.
  2. TV starts. A saved STUN session takes priority; else the most recent LAN server is restored; else onboarding.
  3. TV connects (LAN direct via pinned mDNS entry, or STUN presence → hole punch → QUIC).
  4. TV checks /catalog/thumbprint; if changed, pulls /catalog/manifest.gz; merges every reachable server via CatalogMerger and paints the last-good manifest first.
  5. User selects an entry → /play/{entry_key} with CapabilityProfile. Server reserves from the upload pool, returns a PlaybackPlan (direct or capability-pruned HLS master).
  6. PeerLoopbackProxy exposes the session path as loopback HTTP; Media3 plays. HLS starts conservative (loopback hides real bandwidth) then adapts from segment timings.

Design lineage

Patterns ported from Batocera Fleet Federation / Batocera.Drone: pairing/pinning, transport selection, library delta-sync, transcode sessions. Recovered reference implementations live in docs/reference/. The fingerprint implementation pins byte-for-byte compatibility with the original Python sample-fp-v1.

Technology choices

SWARM is built to be small, private, and free to run:

  • One trusted language for the core keeps the security-sensitive parts consistent and memory-safe.
  • A lightweight desktop app (not a heavyweight browser bundle) so the media server is a small download that stays out of your way in the tray.
  • Standard TV playback components so video uses your device's hardware decoder and just works.
  • Free hosting for the coordinator on a cloud free tier, with automatic HTTPS certificates.
  • On-device subtitles so that feature never sends your media anywhere.

Testing: unit, UAT, integration

SWARM is verified at five layers, from no-hardware backend checks up to real Fire TV UI driven by a real D-pad.

Change control The five closed-loop suites and the orchestrator/cron wrapper are change-controlled. Read .claude/skills/swarm-e2e-suite-lockdown/ before editing any of their test logic or pass/fail thresholds — fix the product bug or report the failure; don't rewrite the test to go green.

Unit

  • cargo test --workspace — plain Rust unit tests, no server, no hardware. Includes the fingerprint vectors pinned byte-for-byte against the original Python sample-fp-v1, contract types, catalog-merge rules, entry-key validation.
  • ./gradlew :core:test (JDK only, no Android SDK) — wire contracts hand-mirrored from swarm-core, with every fixture captured from real serde_json::to_string output, so these are a real cross-language compatibility proof, not internal self-consistency. Also StunApiClient against MockWebServer, and CatalogMerger.
  • This guide has its own unit-style check — cargo test -p swarm-docs — that fails if the guide loses its audience switch, grows a broken in-page link, ships a CDN dependency, or drifts from the facts in README.md / PROTOCOL.md.

UAT (user acceptance)

  • Backend UAT — ./scripts/tests/media_server_uat_tests.sh (wraps apps/server/src/gui_tests/). Real #[tauri::command] handlers invoked directly against a real isolated AppState — real SQLite, real filesystem, real ServerCore — under a mocked Tauri runtime. No hardware, no LAN, ~1 second, CI-friendly. Covers media-root lifecycle, library scan, TV pairing, notifications/errors, metadata editing, MCP tokens. It deliberately does not drive the real WKWebView UI (tauri-driver has no macOS backend) or route through Tauri's simulated IPC/ACL.
  • TV UAT — ./scripts/tests/tv_uat_suite.sh. ~16 scenarios on a real Fire TV, navigated with the real D-pad against the real local media server: stable Compose tags, bounded synchronization, fresh-process persistence tests, capability-aware media selection, failure-evidence bundles. Files its own GitHub issue on FAIL.
  • Resilience — ./scripts/tests/tv_uat_resilience_suite.sh. Opt-in, disruptive transport drop/recovery, kept out of the default run by design.

Integration & interop

  • Multi-node integration harness — tests/integration/. Docker-composed: stun-server + caddy, two headless server nodes, one client node, per-node bridge networks + NAT containers for the hole-punch matrix. The driver exercises register → presence → signal/punch → manifest sync → stream → seek, asserting byte-exactness (fingerprints the received bytes) and timing budgets. Runs in CI on changes to crates/ or apps/stun-server.
  • In-process peer integration tests — apps/server/tests/ (lan_direct_play.rs, http_media.rs, delete_asset.rs): a pinned client pulls the catalog, direct-plays with byte-exact verification, and seeks via Range over loopback QUIC, while an unpinned client is refused at the TLS layer.
  • E2E smoke — ./scripts/tests/tv_e2e_suite.sh. Local media server ↔ real Fire TV(s) on the same LAN, full device fan-out, no UI navigation — every assertion is evidence a real device observed. Files a GitHub issue on failure.
  • Cross-process contract fixtures — the Kotlin :core types are verified against real serde_json output (see the swarm-contract-fixtures skill); ./gradlew :core:interopTest is the opt-in cross-process protocol layer (some legacy fixtures skip since the headless swarm-serverd was removed; new coverage uses an explicitly test-only ServerCore harness).

Orchestration

  • ./scripts/tests/full_uat_suite.sh --github-issue — runs media_server_uat_tests.sh → tv_e2e_suite.sh → tv_uat_suite.sh in order, captures each one's evidence, and files a single consolidated GitHub issue only when at least one test actually failed. Exit code 0 only if nothing failed. --skip-backend / --skip-e2e / --skip-uat / --include-resilience / --device / --all narrow or widen the run.
  • ./scripts/tests/full_uat_cron.sh — continuous-checking wrapper around the orchestrator.

Full detail — scenario catalogs, evidence bundles, device targeting — is in scripts/tests/TV_TESTING.md.
